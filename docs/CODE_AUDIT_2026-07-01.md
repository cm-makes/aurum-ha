### 1. [HIGH] `config_flow.py:694` — remove_device uses substring entity match, deletes other devices' entities (slug-prefix collision)

**Problem:** In async_step_remove_device the cleanup does `if f"aurum_{slug}" in entry.entity_id:` and then `ent_reg.async_remove(entry.entity_id)`. This is an unanchored substring test. Switch entity_ids are `switch.aurum_{slug}_{suffix}` (switch.py:68) and unique_ids are `aurum_{slug}_{suffix}` (switch.py:63). Because slugs are free-text-derived (helpers.slugify) and one slug can be a prefix of another, removing a device whose slug is a prefix of another device's slug wipes the other device's entities too. Concrete scenario: two devices "Washer" (slug `washer`) and "Washer 2" (slug `washer_2`) both pass the add-device duplicate check (distinct slugs). Removing "Washer" evaluates `"aurum_washer" in "switch.aurum_washer_2_override"` -> True, so it removes Washer 2's override/muss_heute/disable switches. A device named "a" (slug `a`) matches `aurum_a...` in almost every other device's entity_id, removing nearly all of them. Contrast with __init__.py:_async_cleanup_orphaned_entities which parses the slug precisely (`entity_slug = "_".join(parts[1:-1])`) and compares by exact set membership.

**Warum ein Bug:** Substring `in` matching instead of an exact/anchored slug comparison causes collateral deletion of unrelated devices' entity registry entries, losing their user customizations (custom name/area/entity_id, restored switch state). The correct entities are only re-created on the subsequent reload, so control switches for the wrongly-removed device are transiently broken and their registry customizations are permanently lost.

**Verifikation (adversarial):** Confirmed real. config_flow.py:694 uses an unanchored substring test `if f"aurum_{slug}" in entry.entity_id:` before `ent_reg.async_remove(entry.entity_id)`. Entity ids are `switch.aurum_{slug}_{suffix}` (switch.py:68) with the slug immediately followed by `_{suffix}`, so a slug that is a prefix of another device's slug matches. slugify (helpers.py:55) maps "Washer"->"washer" and "Washer 2"->"washer_2", distinct slugs that both survive duplicate checks, and "aurum_washer" is literally a substring of "switch.aurum_washer_2_override". Removing "Washer" therefore removes Washer 2's control-switch registry entries; a one-char slug like "a" matches nearly every other device's entities. The correct, precise approach exists elsewhere (__init__.py:56-61 parses entity_slug = "_".join(parts[1:-1]) and compares by exact set membership), confirming this path deviates from intended semantics. Mitigation: the subsequent reload recreates the wrongly-removed switches with their deterministic entity_ids, so functional breakage is transient; the permanent loss is registry customizations (name/area/entity_id override) and RestoreEntity state. No comment, guard, or dead-path negates it. High severity due to the broad collateral-deletion potential of short/prefix slugs, tempered only slightly by functional recoverability on reload.

### 2. [HIGH] `hass_bridge.py:43-47` — Bridge uses synchronous hass.services.call from the event loop (blocking/deadlock)

**Problem:** call_service() (and likewise turn_on/turn_off at lines 49-63, set_state at 38-41) invoke the SYNCHRONOUS ServiceRegistry.call / states.set. In HA core these do asyncio.run_coroutine_threadsafe(async_call(...), loop).result(), which is only valid when called from a thread other than the event loop. The device-control callers in devices.py run inside async_add_executor_job (coordinator.py:230), so they are safe. However BudgetManager.adapt_safety_factor calls self.hass.call_service('input_number/set_value', ...) at budget.py:748, and budget.update()/adapt_safety_factor run directly on the event loop (coordinator.py:182-205, not wrapped in an executor job). Calling the sync services.call from the loop thread blocks that thread on .result() while the scheduled coroutine can never run -> deadlock, or a RuntimeError 'blocking call inside the event loop' in newer HA.

**Warum ein Bug:** The comment says 'fire-and-forget, safe in async context', but blocking=False does not make the sync wrapper non-blocking: the sync ServiceRegistry.call always waits on .result(). Reachable via the safety-factor sync at 17:00 daily when safety_factor_entity is configured; it either hangs the coordinator update loop or raises (swallowed by the broad except at coordinator.py:206, so the input_number never gets updated). Should use hass.async_add_executor_job or hass.async_create_task(hass.services.async_call(...)).

**Verifikation (adversarial):** Confirmed real. hass_bridge.py:43-47 call_service uses the SYNC ServiceRegistry.call (self._hass.services.call(..., blocking=False)). In HA core this is asyncio.run_coroutine_threadsafe(async_call(...), loop).result(); blocking=False does not remove the .result() block on the sync wrapper — it only affects whether async_call awaits service completion. The docstring 'safe in async context' is wrong. budget.py:745-751 (adapt_safety_factor) calls self.hass.call_service('input_number/set_value', ...) via the HassAccess bridge when safety_factor_entity is configured. coordinator.py:144 _async_update_data is async def running on the event loop, and lines 182-204 invoke self.budget.update()/self.budget.adapt_safety_factor(shared) DIRECTLY on the loop, NOT wrapped in an executor — unlike device control at line 230 which correctly uses async_add_executor_job. So the sync services.call executes on the loop thread: run_coroutine_threadsafe(...).result() blocks the loop while the scheduled coroutine can never run -> deadlock, or a RuntimeError in newer HA that is swallowed by the broad except at budget.py:752 (input_number never updated). Reachable once daily: coordinator gate current_hour==17 and minute<1 and adapt_day!=_last_adapt_day (line 202-204), and adapt_safety_factor reaches line 748 whenever target_soc/current_soc are non-None (budget.py 682-693). Severity high rather than critical because it is gated on the optional safety_factor_entity config and fires only once per day, but when configured it is a near-certain daily hang/failure of the coordinator loop. Correct fix: hass.async_add_executor_job or hass.async_create_task(hass.services.async_call(...)).

### 3. [MEDIUM] `modules/devices.py:659` — Startup-detection standby time is counted as device runtime (can permanently block SD start)

**Problem:** For an SD device the Shelly is physically ON during STANDBY (drawing 3-5W). During STANDBY on_since is set once (lines 630-633) but the main loop skips runtime accumulation (lines 243-246 only accumulate when sd_state==RUNNING) and never advances _runtime_tick. When a program is detected, the DETECTED branch calls self._turn_off(...) at line 659, which calls _accumulate_runtime (line 936). In _accumulate_runtime (lines 1000-1007) tick = _runtime_tick or on_since; since _runtime_tick was never advanced during standby, tick points back to when standby began (possibly hours earlier, or HA-restart time via persistence.restore line 193). The full standby-monitoring duration is therefore added to runtime_today_s.

**Warum ein Bug:** runtime_today_s is meant to reflect actual program runtime. Inflating it with idle standby time corrupts reporting/energy stats and, more seriously, feeds _runtime_target_reached (line 462), which is checked in WAITING (line 683). If stop_after_runtime is set with a modest estimated_runtime, the inflated counter can trip the target before the program ever runs on PV, and WAITING returns (False,0) forever (lines 683-685), leaving the SD device permanently stuck and never started.

**Verifikation (adversarial):** Confirmed by the code. During STANDBY the Shelly is turned on via self.hass.turn_on directly (devices.py line 627), not _turn_on, so _runtime_tick is never set; on_since is anchored at standby-start (lines 629/633). The main loop only accumulates runtime when sd_state==RUNNING (lines 243-246), so _runtime_tick stays None throughout standby. On program detection, the DETECTED branch calls _turn_off (line 659) → _accumulate_runtime (line 936), where tick = _runtime_tick or on_since (line 1002); with _runtime_tick None, tick=on_since=standby start, and the full standby duration is added to runtime_today_s (lines 1004-1005). This inflated counter feeds _runtime_target_reached (line 462), checked in WAITING (line 683), which returns (False,0) before the deadline check, so with stop_after_runtime=True (real config, line 149) and a modest estimated_runtime the SD device can be blocked from starting until daily_reset (line 1219). The stated intent (comment line 242: 'SD: only count RUNNING state') is violated by this path. Two reviewer details are imprecise but do not affect the verdict: the _turn_off at 659 uses power_w=0 so energy_today_wh is NOT inflated (only runtime_today_s), and on HA restart persistence.py clears on_since for standby SD (lines 181-184) rather than preserving a far-past timestamp, so the anchor becomes restart/standby-start time. Reporting inflation is guaranteed on every SD detection; the permanent-lockout is conditional on stop_after_runtime config, hence medium.

### 4. [MEDIUM] `modules/devices.py:918` — force_started flag is never cleared on normal turn-on or daily reset (stuck non-sheddable device)

**Problem:** force_started is set True on a deadline force-start of a regular device (line 343). _should_turn_off returns None for any force_started device (lines 519-521), so it is immune to surplus/SOC shedding. force_started is only ever reset inside self._turn_off (line 941) and _sd_reset (line 811). _turn_on (lines 918-931) does NOT reset it, and daily_reset (lines 1212-1223) does not reset it either. If a deadline-forced regular device is later switched off externally (user/HA, not via AURUM._turn_off), force_started stays True; a subsequent AURUM surplus turn-on via _turn_on leaves it True.

**Warum ein Bug:** A normal surplus start is not a forced start, so the device should not retain force-started immunity. Because force_started persists across external off/on cycles and across midnight (daily_reset skips it), the device becomes permanently exempt from surplus and SOC-protection shedding, defeating battery-protection turn-off. A device with no stop_after_runtime can then run indefinitely on grid.

**Verifikation (adversarial):** Confirmed in custom_components/aurum/modules/devices.py. Line 343 sets dev["force_started"]=True on a regular-device deadline force-start. _should_turn_off (lines 519-521) returns None for any force_started device, bypassing both SOC-protection shedding (542-552 "soc_grid_deficit") and excess-deficit shedding (569-581). force_started is cleared ONLY in _turn_off (941), _sd_reset (811), and the SD normal-start path (728). _turn_on (918-931) does NOT clear it, and daily_reset (1212-1223) does NOT clear it. The SD state machine proves the intended contract: line 700 sets force_started=True on an SD deadline start, but line 728 explicitly sets it back to False on a normal "excess_sufficient" start — the regular _turn_on is missing this equivalent reset. Reachable scenario: a regular device with estimated_runtime + muss_heute and stop_after_runtime=False is deadline-force-started (force_started=True); the user turns it off externally (AURUM never calls _turn_off, so force_started persists); on a later cycle _deadline_urgent returns False (line 988 short-circuits once force_started is set) and a normal surplus start via _turn_on (385-387) leaves force_started=True. The device then permanently returns None from _should_turn_off and is immune to SOC/surplus shedding until a MODE_CHARGING/disable event happens (216-228). Because stop_after_runtime=False, the runtime-completion turn-off + _reset_muss_heute (297-305) never fires, and daily_reset does not clear the flag, so the immunity also survives midnight. This genuinely defeats battery-SOC protection turn-off. Severity medium is appropriate: the consequence is real (grid import / blocked battery charging) but it requires a specific device configuration and/or an external off/on toggle, so it is not a universally-triggered critical fault.

### 6. [MEDIUM] `modules/budget.py:187-202 / 506-514` — Weather learning compares previous-hour actual PV against current-hour forecast (hour mismatch)

**Problem:** In update(), `pv_actual_hour_kwh` is only written at the hour boundary (line 189-195) and equals the cumulative delta over the hour that just ENDED (now_h-1). In the same call, `pv_forecast_hour_kwh` is overwritten every cycle with the forecast for the CURRENT hour now_h (line 198-202). `update_weather_learning()` (called by coordinator exactly at the hour boundary) then computes `ratio = actual_kwh / forecast_kwh` (line 514) using last-hour's actual production divided by this-hour's forecast. The two operands are for different hours.

**Warum ein Bug:** The learned per-condition weather factor is trained on a ratio of mismatched hours (e.g. hour-6 actual vs hour-7 forecast), systematically biasing the EMA (especially in morning/evening ramps where consecutive-hour forecasts differ a lot). Both keys are named '..._hour_kwh' implying the same hour; correct learning needs prev-hour actual vs prev-hour forecast.

**Verifikation (adversarial):** Confirmed genuine bug. In budget.py update() the coordinator (coordinator.py:184) runs budget.update() first, then update_weather_learning() at the hour boundary (coordinator.py:190-192, first cycle where current_hour changed). At that boundary cycle: (1) the actual-delta block (budget.py:189-195) fires only when _pv_hour_snapshot_h != now_h, publishing shared["pv_actual_hour_kwh"] = cumulative(now) - snapshot(prev boundary) = production of the hour that just ENDED (now_h-1); (2) the forecast block (budget.py:198-202) runs every cycle and overwrites shared["pv_forecast_hour_kwh"] with the forecast for now_h via next(w for h,w in hourly_forecast if int(h)==now_h) = the hour just STARTING. _get_hourly_forecast (budget.py:761-795) keys forecasts by true clock hour (dt.hour), so forecast[now_h] is genuinely the current/next hour, not the ended hour. update_weather_learning (budget.py:506-514) then computes ratio = actual(now_h-1) / forecast(now_h) — two different hours, despite both keys sharing the '_hour_kwh' suffix. Correct learning needs prev-hour actual vs prev-hour forecast (forecast lookup should use now_h-1). No guard mitigates this: actual is only ever published at the boundary and learning only runs at the boundary, so every daytime (6-20) learning call uses the mismatched pair. The 'ratio<0.05/clamp' guards and the '1:1 port of HELIOS' docstring (which only covers the learning math, not AURUM's shared-key population) do not address the hour offset. Impact is a systematic bias of the per-condition EMA weather factor, worst during morning/evening ramps where consecutive-hour forecasts diverge; bounded by the [0.1,1.5] clamp and EMA smoothing and affecting only a secondary learning feature, so medium severity is appropriate.

**Verifikation (adversarial):** Confirmed in code. async_step_add_device (config_flow.py:599-624) guards slug uniqueness: it computes new_slug = slugify(CONF_DEV_NAME), builds the set of existing device slugs, and rejects a collision with errors["base"]="duplicate_device", with an explicit comment (lines 610-611) that duplicate slugs collide/overwrite entity unique_ids. async_step_edit_device (config_flow.py:649-670) has no equivalent check — it just replaces the matched device via `user_input if d["name"] == name else d` and creates the entry, with no slug-uniqueness (or even invalid/empty name) validation. The orphan-cleanup in __init__.py:32-69 only removes entities whose slug is no longer in active_slugs (handling abandoned old-slug entities post-rename); it does not prevent two live devices sharing a slug. The bug is real but requires the user to deliberately rename to a colliding slug (local config action, not remotely triggerable, partially self-healing for orphans), so medium is appropriate.
